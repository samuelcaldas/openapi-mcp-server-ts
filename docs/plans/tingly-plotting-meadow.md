# Plan: reusable OpenAPI integration SDK and standalone MCP server

## Context

The package currently exposes its CLI as `main` (`package.json` → `src/index.ts`), so importing it from another MCP application starts a process, installs signal handlers, and may exit. Existing reusable pieces (`parseOpenApiSpec`, `registerToolsFromOpenApi`, `prepareServerEnvironment`) are internal, weakly typed, or coupled to global environment settings. Keep the already implemented stdio and Streamable HTTP server, but make both it and library consumers use one secure, composable OpenAPI integration core.

## Proposed implementation

1. **Define the library contract through test-first consumer examples.** Add `src/public.ts` as the side-effect-free package root; retain `src/index.ts` as the executable via `bin`. Expose a small documented, typed API such as `prepare_openapi_integration({ source, base_url, include_tags?, exclude_tags?, validate_output?, credential_provider?, network_policy? })` returning an integration with `list_operations()`, `execute_operation(operation_id, arguments, context?)`, and `register_tools(existing_mcp_server, { prefix? })`. Direct execution returns `{ status, data }` in a typed result and throws actionable, secret-safe errors; registration converts results/errors to MCP responses without leaking credentials. The host supplies a validated request authentication context when using user delegation; the SDK never performs inbound HTTP authentication on the host's behalf. No CLI initialization, process signals, network request, or UI load on package import. Default registration adds only OpenAPI tools; prompts and UI remain explicit/standalone concerns. Keep existing tool names in standalone mode; namespace distinct integrations when embedding several specs and fail fast on collisions.

2. **Extract a typed shared integration core rather than duplicate server logic.** Reuse `src/utils/openapi.ts` for object/file/URL loading and dereferencing, `src/utils/url_validator.ts`/`httpClient.ts` for SSRF-safe requests, and existing parameter/schema mapping in `src/tools/index.ts`. Split operation discovery, input validation, HTTP execution, and MCP registration into focused modules under `src/integration/` (plus thin `src/tools/` adapters); replace public `any` and positional overloads with small option/result/context interfaces. Keep path/query/header/body handling, response validation, tag filtering, and multiple specs; retain existing deep-module helper signatures as thin compatibility adapters while standalone and the new package root use the same typed core. Make validation and prompts per-integration configuration, not the module-level `config` snapshot; inject HTTP and credentials per instance/request. Use the existing `validateOpenApiSpec` in `src/utils/openapi_validator.ts` to reject invalid specs; reject invalid URLs/operations and malformed extra spec entries with actionable, entry-indexed errors instead of silently omitting them. Preserve existing behavior where not intentionally changed. Keep prepared entries immutable from the perspective of concurrent request handlers, and avoid process-global credential/provider caches or raw-token cache keys for SDK callers; scope service caches to their owning integration, include every credential-affecting option in cache identity, and never cache exchanged user tokens across callers.

3. **Make standalone mode an adapter of the same integration.** Map `loadConfig`/`validateConfig` and `prepareServerEnvironment` (`src/server.ts`, `src/utils/additional_specs.ts`) to the shared preparation and registration; keep `createServerInstance` creating fresh MCP servers from prepared entries, with prompts and `registerUiApp` only as standalone additions. Register shared workflow prompts once in multi-spec mode and fail fast on duplicate operation identifiers unless namespaced. Preserve `src/transports/stdio.ts`, `src/transports/http.ts`, and HTTP inbound authentication policies, but enforce the inbound-auth and delegation checks from `src/utils/config_validator.ts` at any programmatic listener startup as well as CLI entry, so direct callers cannot bypass remote-auth checks. Preserve port `0` for existing programmatic ephemeral-listener tests while retaining strict CLI port validation. For non-loopback binding, require explicit Host/Origin allowlists and declared trusted proxies (never trust every proxy); Origin need not be present on non-browser MCP clients, but must match when provided. Keep transport cleanup and signal handling inside the executable, ensure shutdown/connection failures close resources once, and never install host-process signal handlers from SDK imports. Move no CLI parsing, listener setup, environment reads, signal handling, or UI asset resolution into the library root. Retain the existing CLI flags and transport semantics.

4. **Keep credential and network isolation across both modes.** Test user delegation, service mode, concurrent callers, multiple integrations, and operation-provided header casing. In user mode, do not install a service-auth interceptor on the HTTP client (including additional specs); always derive the destination token for that request without fallback, passthrough, or shared user-token caches. Ensure the RFC 8693 exchange uses a DNS-pinned, redirect-disabled, bounded request rather than validating then posting with unpinned Axios. Reject case-insensitive Authorization overrides from OpenAPI parameters. Keep external-URL SSRF restrictions, inbound OAuth/bearer checks, and per-request MCP-server isolation; document that embedded hosts own inbound authentication and that remote standalone TLS termination/allowlists remain required. Avoid broad IdP/proxy redesign beyond securing the affected SDK and standalone boundaries.

5. **Publish a real SDK entrypoint without breaking the CLI.** In `package.json`/`tsconfig.json`, point `main`, `types`, and `exports["."]` to compiled `src/public.ts` JavaScript and generated declarations; retain `bin` and `manifest.json` → `dist/index.js` and the existing UI build. Update `README.md`, `docs/streamable-http.md`, and `docs/sdk-integration.md` with examples of importing into an existing `McpServer`, direct operation execution, multiple spec prefixes, security responsibilities, and standalone CLI usage. There is no `docs/README.md` in this checkout. Avoid publishing secrets or changing remote infrastructure.

## TDD and verification

- For each change: write a single behavioral failing test, run it and confirm the intended RED, implement the smallest GREEN, then refactor with the full suite green. Apply SOLID and Object Calisthenics to touched code: one indent level, no `else`, one dot per line, meaningful domain types and collection wrappers where useful, descriptive names, functions ≤15 lines, classes ≤100 lines and ≤2 fields, modules <200 lines, no public getters/setters; add concise docstrings to every public API. Start with package import from an isolated consumer (no startup/exit or new SIGINT/SIGTERM handlers), generated type declarations, existing-server tool registration, and direct operation execution; use real MCP `Client` + `InMemoryTransport` calls/local API fixtures, not SDK-private `_registeredTools` or placeholder assertions.
- Exercise one spec through embedded MCP and through standalone stdio and `POST /mcp`: initialize, list tools/prompts, invoke path/query/body operations, verify response validation and tag filters; test simultaneous calls and two differently configured integrations for no credential/configuration leakage. Keep OAuth/Host/Origin/405 behavior; assert direct programmatic remote startup rejects unauthenticated or unallowlisted listeners, while loopback port `0` remains usable. Verify user delegation failures never reach the destination API.
- Run focused tests at each RED/GREEN stage and finally `npm test`, `npm run validate`, `npm run build`, and `npm pack --dry-run`; install the tarball in a clean temporary consumer to typecheck/import the package root without side effects and run the CLI `--help`, stdio, and HTTP smoke tests. Run available documentation/static checks. During implementation only, sync/rebase according to repository policy before work and before merging; do not merge or publish as part of planning.
