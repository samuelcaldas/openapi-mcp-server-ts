## Contexto

O servidor TypeScript já inicia por stdio ou por HTTP+SSE legado, mas não oferece o transporte Streamable HTTP moderno nem um executável distribuível via npm. O SSE atual compartilha um único transporte entre clientes e escuta sem autenticação de entrada; o CLI também duplica a criação do servidor de `src/server.ts`. O objetivo é preservar stdio, oferecer `/mcp` seguro a clientes remotos e executar o pacote instalado via npm/npx. Por decisão do usuário, não há requisito de compatibilidade com `/sse` e `/message`; a autenticação remota prioriza identidade por usuário via OAuth 2.1 e token exchange, aceita conta de serviço configurada explicitamente e oferece token bearer fixo como alternativa. Não publicar no registro npm nesta etapa.

## Abordagem

1. **Unificar inicialização e validar configuração.** Em `src/index.ts` e `src/utils/config.ts`, usar `loadConfig` e uma fábrica comum do servidor, com `--transport stdio|http` (padrão `stdio`), `--host`, `--port` e variáveis de ambiente equivalentes. Rejeitar tipos desconhecidos, host/porta inválidos, combinações de autenticação incompletas e `--transport sse` com mensagem de migração para `/mcp`; nunca cair silenciosamente em stdio. Refatorar `src/server.ts` para preparar especificações e configuração uma vez e registrar ferramentas, prompts e `registerUiApp` em uma nova instância `McpServer` por conexão/requisição. Reutilizar `parseOpenApiSpec`, `validateUrlForSpec`, `createHttpClient` e o controle `allowed_spec_dirs`; preservar múltiplas especificações e filtros de tags. Evitar buscar a especificação novamente a cada POST.

2. **Implementar HTTP MCP no SDK existente.** Criar `src/transports/http.ts` usando `StreamableHTTPServerTransport` de `@modelcontextprotocol/sdk` e Express, endpoint único `POST /mcp` e modo stateless explicitamente configurado; delegar enquadramento JSON-RPC e eventual SSE **na resposta ao POST** ao SDK. Retornar 405 para GET/DELETE se o modo stateless não oferecer esses recursos. Limitar corpo e conexões, isolar o servidor/transporte por requisição e limpar recursos após resposta, desconexão e SIGTERM/SIGINT. Aplicar bind real a `host:port`; manter stdio em `src/transports/stdio.ts` ou no ponto de entrada. Remover o ramo legado `/sse` + `/message`, sem introduzir novo endpoint SSE. Verificar a versão/protocolo efetivamente suportados pelo SDK 1.x antes de prometer compatibilidade com revisões MCP posteriores.

3. **Proteger acesso remoto antes de expor o listener.** Criar módulo próprio de autenticação de entrada (por exemplo `src/auth/inbound.ts`) separado de `src/auth/index.ts`, que autentica **a API de destino**. OAuth: usar o middleware/verifier do SDK com biblioteca consolidada de JWT/JWKS; validar assinatura, emissor, audiência do recurso MCP, expiração, escopos e identidade, usando JWKS do emissor configurado, nunca URL indicada pelo token. Servir metadados OAuth Protected Resource (RFC 9728) acessíveis sem token e desafios `WWW-Authenticate` corretos; IdP/authorization server é externo. Suportar apenas JWT assinado inicialmente, documentando que tokens opacos exigem introspecção futura. Alternativa `bearer`: segredo exclusivo em ambiente/arquivo de segredo, verificação em tempo constante e sem descoberta OAuth. Modos `none|oauth|bearer` são mutuamente exclusivos; fora de loopback, proibir `none`. Não aceitar segredo por flag de CLI nem registrar tokens. Validar `Origin` e `Host` com allowlists explícitas, inclusive atrás de proxy; exigir URL pública HTTPS para OAuth remoto, TLS no proxy reverso e confiança apenas em proxies declarados. Não automatizar Nginx Proxy Manager: documentar configuração manual, bloqueio de acesso direto e encaminhamento de cabeçalhos necessários.

4. **Preservar identidade até a API de destino sem token passthrough.** Em `src/tools/index.ts`, `src/server.ts` e um provedor dedicado de credenciais, passar o principal validado pelo contexto `authInfo` do SDK à execução da tool. No modo prioritário `user`, trocar o token recebido **com audiência MCP** por um token específico da API via OAuth 2.0 Token Exchange (RFC 8693) em IdP confiável, com audience/resource e escopos configurados por API; usar cliente HTTP/headers por requisição, sem mutar defaults globais. Falhar fechado se troca, escopo ou configuração da API faltar; nunca encaminhar diretamente o token MCP à API nem usar automaticamente a credencial compartilhada como fallback. No modo opt-in `service`, usar a autenticação de saída já existente; este é o único modo permitido para stdio e para bearer fixo de entrada (que não identifica usuários individualmente). Validar destinos de troca de token com as proteções de URL/SSRF existentes, não aceitar cabeçalhos de operação capazes de substituir `Authorization` delegado e não compartilhar caches de credenciais entre usuários.

5. **Empacotar a CLI completa.** Em `package.json`/`package-lock.json` e `src/index.ts`, incluir shebang Node no JavaScript compilado, `bin` apontando para `dist/index.js`, corrigir `main`, definir `files` e `engines`, e construir Vite (`dist-app/`) antes de `tsc` no build de distribuição. Em `src/app.ts`, localizar `dist-app/index.html` relativamente ao pacote instalado, não ao diretório corrente; verificar compatibilidade entre `@modelcontextprotocol/ext-apps` e SDK existente sem impor migração do SDK não relacionada. Preservar MCPB (`manifest.json`) e corrigir sua invocação/argumentos se o smoke test demonstrar divergência. Atualizar `README.md`, criar documentação operacional em `docs/` e preencher `.env.example` apenas com nomes/valores fictícios: exemplos stdio, npx, `/mcp`, OAuth + troca por usuário, conta de serviço, bearer fixo, TLS/proxy e descontinuação do SSE legado.

## Verificação

- Testes unitários de configuração, precedência CLI/ambiente, modos inválidos, autenticação de entrada e escolha explícita de credenciais da API; teste negativo de cabeçalhos `Authorization` fornecidos pela especificação e isolamento entre usuários.
- Testes de integração com cliente MCP do SDK: stdio e `/mcp`, listar tools/prompts e executar uma operação OpenAPI local simulada; dois clientes simultâneos sem vazamento de resposta ou credencial, POST JSON e SSE de resposta se o SDK optar por streaming, GET/DELETE 405 no modo stateless.
- IdP e API simulados: JWT válido/expirado/emissor-audiência-escopo incorretos; metadata/challenge OAuth; token exchange com audience correta; indisponibilidade do IdP sem fallback para serviço; token fixo certo/errado; HTTP externo recusado quando sem auth, Origin/Host inesperados recusados.
- `npm run validate`, build de distribuição, `npm pack --dry-run` e instalação local do tarball para executar a CLI fora do repositório (`--help`, stdio e HTTP com cliente MCP); confirmar `dist/` e `dist-app/` no tarball, ausência de `.env`/segredos e funcionamento da UI. Validar documentação com checagens estáticas disponíveis. Não publicar npm nem configurar NPM programaticamente.

## Restrições e pressupostos

A implementação usa o SDK já presente como primeiro caminho, sem prometer suporte à revisão mais recente do protocolo que ele não implemente. A troca por usuário requer IdP compatível com RFC 8693 e audiência configurável para cada API; sem isso, o modo `user` não inicia, enquanto o modo `service` permanece uma alternativa explícita. O proxy remoto precisa oferecer HTTPS e regras de acesso; configuração concreta de hostname, IdP e secrets será fornecida pelo operador, nunca embutida no código.
